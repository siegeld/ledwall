# Driving ICN1065L panels

The P1.25 320×160 mm modules (256×128 px) use **`ICN1065L`** — a Scramble-PWM
driver, not a shift register. Nothing in this repo's HUB75 output stage can drive
them. This page is the protocol, so the work can start from fact rather than
reverse engineering.

> **Status: not implemented.** `gateware/hub75.py` shifts 1-bit planes and does
> its own BCM. Everything *upstream* of the output stage — pixel DMA, the packet
> classifier, the framebuffer, the hardware buffer swap — is unaffected and
> stays as it is.

## Why the receiving card was never the problem

Colorlight's own 5A-75E specification V8.0 says **"supports up to 1/64 scan"**
with 32 RGB groups, while the board exposes only five parallel row-address lines
(`A`–`D` buffered, `E` on a repurposed GND pin). Both are true, because **these
panels do not use parallel row addressing at all** — the driver IC holds an
internal scan counter, advanced by `OE` pulses and reset by VSYNC.

That is the thing to internalise before buying panels: **pixel pitch, module size
and receiving card tell you nothing about whether this repo can drive them. Ask
for the driver IC part number.** Shift-register parts (MBI5124, ICN2038 in
compatible mode) work with what is here. Anything advertising 13–16 bit greyscale
or refresh much above 3 kHz is almost certainly S-PWM and needs its own output
stage.

## Commands are LAT pulse widths

There is no command/data line. The chip counts how many CLK cycles `LAT` stays
high:

| Command | LAT-high CLK cycles | Meaning |
|---|---|---|
| `V_SYNC` | **3** | reset the internal row counter |
| `REG_LATCH` | **5** | commit one configuration word |
| `PRE_ACT1` | **11** | unlock register writes |
| `PRE_ACT2` | **14** | confirm register writes |
| `CLK_PAD` | 8 | padding between commands, LAT **low** |

## Frame prefix

Sent at the start of every frame:

```
VSYNC(3)      → pad(8)
PRE_ACT1(11)  → pad(8)
PRE_ACT2(14)  → pad(8)
0x00AA  LAT(5)      wrapper 0
0x01AA  LAT(5)      wrapper 1
REG[n]  LAT(5)      one configuration register
0x0055  LAT(5)      wrapper 2
0x0155  LAT(5)      wrapper 3
```

The four wrapper words are magic values that distinguish a register write from
pixel data. **One register per frame**, cycling through all 38 — so the full
configuration is refreshed about every 38 frames rather than written once.

A quiet region of ~704 all-zero clocks is inserted *before* the VSYNC train in
the reference driver, pausing row scanning while the command train latches. It
is edge-count neutral — no `OE` pulses added or removed — so the chip's row
pointer cannot drift.

## The 38 configuration registers

High byte is the register index, low byte the value:

```
00aa 01aa 022a 0335 0412 0500 0601 0720
0c18 0d01 0e86 0f01 1040 1127 1200 1300
1400 1500 1600 1800 1906 1c60 1dca 1e73
1f00 2000 2100 2200 2300 2400 2500 2600
2700 7000 7100 7200 7300 74a0
```

Index **2** is the scan-line count and is the one that must be computed rather
than copied:

```
REG[2] = 0x0200 | (rows_per_frame - 1)
```

The table above carries `0x022a`, i.e. 43 rows — the reference panel. **A
256×128 module at 1/64 scan needs `0x023f`.**

## Pixel data

Per row, per chain: **16-bit SPWM words, bit-serial, MSB first**. The bottom 12
bits are greyscale (4096 levels); bits 15..12 must be zero. Each output word
carries one bit from *every* colour channel at once:

```
for j = 15 downto 0:
    word = 0
    if r1 & 0x8000: word |= BIT_R1
    if g1 & 0x8000: word |= BIT_G1
    if b1 & 0x8000: word |= BIT_B1
    if r2 & 0x8000: word |= BIT_R2      # lower half of the panel
    ...
    emit(word)
    r1 <<= 1; g1 <<= 1; ...
```

So the chip does the PWM. There is no bit-plane cycling, no BCM, and the gamma
LUT in `hub75.py` becomes an 8-bit → 12-bit gamma curve instead — see
`Icn1065Gamma`, which is where most of the logic in this stage ends up going.

## Row scanning

After the pixel rows, a suffix cycles the row addresses. **Each `OE` pulse
advances the internal scan counter by one.** `OE` is **active HIGH** on this
part, the opposite of a plain HUB75 panel.

| Constant | Value | Meaning |
|---|---|---|
| `ROW_OE_LEN` | 128 | CLK cycles per row slot |
| `ROW_OE_CNT` | 1 | OE pulses per slot (2 CLK: rise + fall) |
| `ROW_OE_ADD_LEN` | 126 | hold cycles making up the rest |
| `OE_LEN_REGULAR` | 4 | |
| `OE_LEN_RESTART` | 12 | |
| `OE_DELAY_AFTER_ADDR` | 20 | |

The reference calls the slot width *"the most important tuning parameter for this
panel"*.

## Corrections made while implementing this

Two things in the README above are misleading, and the source settles both.

**A register block is a full row of clocks, not five.** "0x00AA data, 5 LAT
clocks" reads as a five-clock command, but a 16-bit word cannot shift out in
five clocks. `setDataRegBuffer_n()` shows what happens: the block is
`pixels_per_row` clocks long, the word is shifted MSB-first **once per driver
IC** to fill it, and LAT is asserted only for the final 5 clocks. Each ICN1065
has 16 channels, so a 256-column module has 16 in the chain and 16 × 16 bits
exactly fills the row. That is not a coincidence — it is why the block is a row
long.

**The pixel stream cannot stall.** The panel clocks data on every CLK, so a gap
between pixels shifts the remainder of the row by that many bits. A first
implementation here used a two-state fetch between pixels and the full-frame
simulation caught it immediately: 19 clocks per pixel instead of 16, a 16%
overrun. The serialiser now reloads in the same cycle the last bit leaves.

## What this means for the gateware

`RowColorOutput` and the bit-plane machinery in `gateware/hub75.py` are the wrong
shape. A new output stage needs:

1. a **command encoder** — emit a LAT pulse of N clocks with padding;
2. a **prefix sequencer** — VSYNC, PRE_ACT1/2, and one wrapped register write per
   frame, cycling 0..37;
3. a **bit-serialiser** — 8-bit framebuffer pixel → 12-bit brightness → 16 bits
   shifted MSB-first, six channels packed per emitted word;
4. a **row scanner** — OE pulses on a 128-clock slot, active HIGH.

...plus two more that turned out to matter as much as the protocol itself:

5. a **pixel source** — `Icn1065PixelSource`, two framebuffer reads per request
   (upper and lower half of the panel), with a `GAP` cycle between them because
   a memory that holds `ack` high will otherwise serve the second read from the
   first read's data;
6. a **gamma unit** — `Icn1065Gamma`, 8 bits to 12, piecewise-linear over 16
   segments, combinational so it costs no clocks in a path that cannot stall.
   One set of three serves all nine outputs (`Icn1065SharedGamma`), because
   behind one arbiter every source reads the same returning data bus;
7. a **pipelined arbiter** — `Icn1065PipelinedArbiter`, which turned out to be
   the piece the whole design rests on.

The stage is parametrised on RGB groups per connector — `GROUPS_HUB75 = 2`,
`GROUPS_HUB320 = 4` — because HUB320 is a width change and not a protocol one:
same CLK, LAT and OE, same driver ICs, twelve data lines instead of six driving
four horizontal slices instead of two. Eight HUB320 outputs place at 23%% logic
and 50%% of the IO, which is 1.8x the pixels of the nine-output HUB75 wall for
3%% more logic. `docs/BENCHMARKS.md` §4d has the numbers and the pin-mapping
caveat.

All of it is on `main` as of v2.0.0 and simulated — 93
checks, `./build.sh sim-icn1065`. The nine-output stage placed at **20% logic,
zero block RAM and zero DSP** up to gateware 1.28.0, timing passing at 64.9 MHz
against 40 (`./build.sh fit-icn1065`).

**That is no longer true, and the block RAM is now the binding constraint.**
The scan-out line buffer added in 1.29.0 costs **5 EBRs per output**, derived
rather than guessed: it is `3 * groups * grey_bits` = 156 bits wide by
`2 * columns` = 512 entries, and a DP16KD is at most 36 bits wide, so it needs
ceil(156/36) = 5 in parallel -- which is also exactly its capacity,
ceil(79,872/18,432) = 5. (An earlier revision of this section said 6, from
dividing a measured total, and that one wrong EBR is what made it claim three
outputs were impossible.) Measured on the real device for the 1.30.0
one-output E320 build:

| Resource | Used | Of | |
|---|---|---|---|
| DP16KD (EBR) | **47** | 56 | **83%** |
| MULT18X18D | 4 | 28 | 14% |
| TRELLIS_IO | 89 | 197 | 45% |

So the fixed cost is 42, and the budget is:

| outputs | line buffer | total | |
|---|---|---|---|
| 1 | 5 | 47 / 56 | fits |
| 2 | 10 | 52 / 56 | fits |
| 3 | 15 | **57 / 56** | over by **one** |

**Three outputs is over by a single EBR.** That is a budget exercise, not an
architectural wall — and it matters because **stock Colorlight firmware drives
three of these modules at 20 fps on this same LFE5U-25F**, so any claim that
the part cannot do it is a claim about THIS design. Candidates to free, largest
first: the BIOS ROM (`0x88bc` = 35,004 bytes), `burst_fifo` (2048 x 40 bits,
~5 EBR — itself widened from 512 for RB-5524, where 1536 would still hold about
four packets), the palette (512 x 32, ~1 EBR), and the VexRiscv caches. The
Ethernet MAC slots are already minimal at `nrxslots`/`ntxslots` = 2, cut from 8
the last time this bit.

Logic is NOT the constraint: the one-output build is 17,296/24,288 LUT4 (71%),
and §4d measured the marginal cost of an output at roughly 576 LUTs, so three
outputs is about 76%.

**The nine-output HUB75 preset would need 45 EBR of line buffer and cannot be
built at all with it enabled** — it was never rebuilt after 1.29.0, so the
20%-logic figure above describes a configuration that no longer exists.

Do not quote the old figure. Re-measure with `./build.sh fit-icn1065` and read
`Device utilisation` out of the nextpnr log; the timing gate now prints a
verdict for every clock alongside it.

**The arbiter is worth reading about before anything else here.** A blocking
round-robin arbiter — hold the port, read, wait, release — has only one read in
flight, so a pixel pair costs `2 x sources x latency`. At a realistic 16-cycle
LiteDRAM latency that is 291 clocks and a **7.7 Hz** wall. The data itself fits
the SDRAM budget comfortably; a blocking arbiter simply converts a latency into
a throughput limit. Issuing commands without waiting, and matching returning
data by tag, brings the same case to 46 clocks. `docs/BENCHMARKS.md` §4c has
both tables.

What is **not** built: the wiring into `colorlight.py`. Until the stage and the
SoC are placed together once, "does it all fit" stays an arithmetic answer.

## Which variant — this decides whether any of this works

The part is **Chipone `ICND1065`**. This file and the gateware say "ICN1065"
throughout, which is the wrong string to put on a purchase order.

The reference driver states it is compatible with **`ICND1065L`** and
**`ICND1065S`**. It is NOT compatible with **`ICND1065(AP)`**, which
[issue #2](https://github.com/nimakolahi/hub75-icn1065/issues/2) reports "has
differently numbered registers and definitely other differences". Same family
name, different protocol, and nothing here would drive it.

So when ordering, the driver IC has to be pinned down in writing:

| Driver IC on the module | Works with this stage |
|---|---|
| `ICND1065L` | yes |
| `ICND1065S` | yes |
| `ICND1065(AP)` | **no** — different register numbering |
| `DP3364S` | table present, **untested**, and the row timing is unverified |
| `DP3264S` | table present from gateware 1.2.0 — see below |

> The `DP3364S` row of this table said "no, different chip entirely" until
> 2026-10-16. That was true when written and stopped being true when
> `spwm_chips.py` gained a table for it; the doc was not updated with the code.
> Check the `CHIPS` registry in `gateware/spwm_chips.py`, which is the authority.

This is not hypothetical. Three specifications for what appears to be the same
320x160 mm P1.25 64-scan module have arrived from suppliers, naming
`ICN1065L`, `DP3364S` and `ICND1065S` respectively. Identical pitch, identical
size, identical scan rate, identical 3840 Hz refresh — and one of the three
cannot be driven by any of this code. `docs/HARDWARE.md` section 8d already
says the driver IC part number is the only thing worth trusting; this is that
lesson arriving in the post.

Connector pinouts differed too — 26P on one spec, 36P on another, neither of
which is HUB75 (16P) or HUB75E (20P). That needs pinning down separately, and
before a receiver card is chosen.

## The DP3264S — same family, different ROW signal

> **The DP3365S is the same family again**, and its datasheet
> (`docs/datasheets/DP3365S_Rev1.0_EN.pdf`, from Linsn 2026-10-20) is the
> clearest statement of the rules this stage implements: identical LE
> instruction widths, the same channel-15-first data order, the same
> VSYNC/PRE_ACT/WR_CFG/LAT frame order, and in 11.7.3 the W12 cadence stated
> in words -- *"There is only one W12 in every Numbers of row signal, (Numbers
> of row signal = numbers of groups x numbers of scans)"*. It is a superset:
> 16-bit grey, up to 128 display groups, a DDR/SDR edge-mode switch and an
> extra `reg0x14[3]` that lengthens the row -- register-compatible for
> everything we drive. Linsn's CURRENT production module uses it; the bench
> sample is marked DP3264S.

Added 2026-10-16, driven by the first P1.25 module actually arriving on the
bench. The module's markings are **`DP3264S`** (the S-PWM driver) and
**`HX6158HSP`** (the row/scan driver), on a HUB320 connector.

### It is not the DP3364S, and one digit was the whole problem

Both parts exist, both are real, and this repo already had a table for the
other one:

| | `DP3364S` | `DP3264S` |
|---|---|---|
| Supply | 2.6–5.5 V | 3.5–5.5 V |
| Registers | 15 in our capture | **13**, `0x02`–`0x0D` plus `0x11` |
| `0x0E` `0x0F` `0x15` | written by our table | **Reserved** |
| `0x0C` SYNC_MODE | mode 1 in our table | **2** = high-gray independent refresh |
| ROW pulse | uniform | **W12 then W4** |

Pointing the `dp3364s` table at a `DP3264S` panel produced a **completely dark**
module — not dim, not scrambled. That symptom is the tell: the registers were
plausible enough to load and the row signal was never valid, so no row ever
started.

### What actually made it dark

Datasheet §11.5. The DP3264S generates GCLK on-chip, so the pin that is `OE` on
an ordinary constant-current part becomes a **ROW** signal. Its rising edge
starts a row and **its high width carries meaning**:

* **W12** — 12 DCLK — for the first row of group 0
* **W4** — 4 DCLK — for every other row

This stage emitted a uniform **2-clock** pulse (`ROW_OE_PULSE`), which is neither.
From gateware **1.2.0** the width is runtime state: `chip_cfg.row_pulse` and
`chip_cfg.row_pulse_first`, defaulted per chip from `spwm_chips.py` and written
by the firmware at boot, so one bitstream still serves the whole family.

`ROW_OE_LEN` (the 128-clock slot) is unchanged and remains the reference's "most
important tuning parameter" — it is the *period*, not the pulse.

### The current register is not a knob to guess at

The published profile for this panel class sets `0x08` to `0xBF`. The datasheet
gives `reg08[5:0] = round(128*IGAIN/(reg08[7:6]+1))-1`, with `[7:6]` a 50%
gain step — so **`0xBF` is 150% of nominal drive current** and `0x7F` is 100%,
which is also the part's own default. Our table ships `0x7F`. Raise it
deliberately if the panel is dim; do not copy a profile's value into a module
whose binning you do not know.

### Where the numbers came from

Registers are `dp3264_regtype9` from **`board707/DMD_STM32`**,
`register_test/profiles/dp3264/dp3264_scan_64.h`, labelled
"P1.25 - DP3265 - 5368 - 1/64" at 12-bit grey — the closest published profile to
this module. That catalogue's naming is `pitch - driver - rowchip - scan`, which
is worth knowing: it is the only place seen so far that records the **row** chip
alongside the driver, and on these modules both matter.

The library's own grouping also settled the architecture question before any
code was written: it puts `DP3264` and `ICND1065` in the **same** class — "PWM
timing (DCLK) and row switching (GCLK) through completely independent signals" —
which is why this was a pulse-width change rather than a new output stage.

### Reading a vendor bitstream, if you ever need to

`ecpunpack` will not open a Colorlight image as shipped: it reads every config
frame, reports `program DONE`, then dies on `unsupported command 0x01`, an
8-byte Diamond trailer. Truncate those 8 bytes and it unpacks. See
`docs/HARDWARE.md` §1c.

## ROW must never stop -- the fault that made every other experiment meaningless

Found 2026-10-17 by reading `DP3264S_REV2.0` section 11.6.2, after the panel had
stayed dark through three row-address mappings, three chip tables, both
data-path states and a twelve-point live sweep.

The register table selects `reg0x0C[7:6] = 2`, **high-grey independent refresh**.
The datasheet's rules for that mode are explicit:

> "4. ROW is sent continuously at a fixed display frequency **without
> interruption**. The frequency of ROW is 1/the display time of one row = 1/the
> time between two ROW rising edges."
>
> "5. Group 0, row 0 sends ROW signal W12, otherwise sends ROW signal W4. There
> is only one W12 for each (number of groups x number of rows scanned) ROW
> signals, and it keeps circulating in this way."

ROW is not a row-advance convenience on this part. 11.5: the on-chip GCLK
generator "changes the OE signal of the general constant current chip to the ROW
signal", and its rising edge "indicates the beginning of a row of display". **ROW
clocks the display engine.** Stop it and the panel stops, however correct the
pixel data, the registers and the row address are.

`Icn1065Output`'s FSM emitted ROW only in a dedicated `SCAN` phase, *after* all
the pixel data for the frame:

| phase | clocks at 256 columns, 64 rows | ROW pulses |
|---|---|---|
| prefix | ~1,332 | none |
| pixels | `columns x rows x 16` = 262,144 | none |
| scan | `rows x 128` = 8,192 | 64 |

**ROW absent for 97% of every frame.** That is a dark panel, and dark
*invariantly*: while the display engine is stalled, no row mapping, chip table,
latch setting or pulse width can make a difference -- which is precisely what
weeks of sweeping those four things kept finding. `refresh_count` climbed the
whole time, because it counts the gateware's scan state machine and not light;
`CLAUDE.md` warns about exactly that.

Only 11.6.1's **general frame synchronisation** mode (`reg0x0C[7:6] = 0`) permits
the burst shape -- there, display "stops until the next VSYNC arrives". We
selected mode 2 and drove it like mode 0.

**The fix** is `scan.start.eq(~scan.busy)` as an unconditional combinational
assignment: the row scanner free-runs always, through the prefix and the pixel
phase, instead of only between frames. Concurrency is safe because the paths are
independent -- the scanner drives ROW alone, the data path drives CLK/LE/SDI
alone. board707's survey classifies this family the same way: "timing is handled
by the clock signal, while row switching is driven by OE pulses; the two signals
are completely independent."

### What the same reading confirmed, and one thing it did not

Confirmed correct in the existing implementation:

* **W12/W4** (11.5) -- `row_pulse=4`, `row_pulse_first=12`.
* **LE command widths** (11.1) -- `DATA_LATCH` 1, `VSYNC` 3, `WR_CFG` 5,
  `PRE_ACT` 14.
* **One register per frame** (11.4): "each frame can only write the register
  value of one address, and 13 frames are required to complete the refresh of
  all registers" -- which is what `slots=1` with a rotating slot does.
* **Greyscale width**: 11.4 says the part "only receives the lower 14 bits" of
  the 16-bit word -- but that is the part's MAXIMUM, reached only at
  `reg0x04 = 0x3f`. What it actually DISPLAYS is `4 x (reg0x04+1) x
  (reg0x03+1)` (11.7.5), which at this module's factory registers is
  `4 x 32 x 64 = 8192` -- **13 bits**, matching the vendor profile's
  `grayScale: 8192`. `GREY_BITS` is now computed from the register table
  rather than fixed, so the two cannot disagree. A 14-bit build showed no
  coherent picture at all, and 12 bits (every build before 2026-10-19) used
  half the range and washed out every mixed colour. See E320-BRINGUP 4.10.

**Settled on glass (2026-10-19)**: 11.2 gives the data order within a line as
channel **15 down to 0**, while the FSM walks `chan` 0 -> 15 ascending. On this
module's wiring the ascending walk is the one that lands columns in order
(`chan_rev = 0`; reversing breaks a diagonal into mirrored 16-pixel segments),
and no column pair swap is needed either (`chan_xor = 0`, retired in
`E320-BRINGUP.md` 4.6b). The one remaining data-order correction is
`sweep_adv = 1` (4.6a).

### Where rows actually come from

The application schematic on page 1 settles the question `docs/HUB320.md` was
chasing. The DP3264S has **no address pins** -- the pin table gives it `SDI`,
`CLK`, `LE`, `ROW`, `SDO`, `REXT`, and sixteen outputs. Row selection belongs to
a separate **"Line Drive Unit"**, driven by the controller over its own
`LINE SELECT` / `DATA` path. So A/B/C on HUB320 pins 17-19 are the serial link to
the `5958` row driver, not a binary address -- which is what Colorlight's own
software implied by filing `DM5953/5958` under the 595 shift-register family.
